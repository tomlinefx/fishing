## Way of Working

私たちは**トランクベース開発**で進めます。作業の起点も合流先も `main` ひとつで、長く残るブランチは作りません。

- 各 Bolt（Construction の一区切り）は `main` から切った短命ブランチ `bolt-<slug>` で作業し、完了したら `main` に **squash-merge** します。Bolt ひとつが `main` の1コミットになり、`main` の履歴が Bolt の順番と1対1で対応します。中間コミットは squash で消えますが、監査ログ（`<record>/audit/`）に経緯が残るので許容します。
- Construction の worktree 設定は base ブランチ `main`、merge 先 `main`、strategy `squash` です（フレームワークの `aidlc engine worktree` の既定フラグと同じ）。
- `main` への直接コミットは行いません。README や設定の微修正であっても Bolt ブランチ経由で取り込みます（開発者が1人でも、この線を守ることで「`main` が緑である」という判定と、後述のロールバック手順が成り立ちます）。
- 手でブランチを切る場合は kebab-case とし、`bolt-` 接頭辞は使いません（フレームワークの worktree ブランチと衝突させないため）。
- squash 後に `main` に残るコミットメッセージは `<bolt-slug>: 1行要約` の形にすることを推奨します（監査ログの Bolt slug と突き合わせやすいため）。コミット文は日本語で構いません。
- リポジトリは GitHub などのリモートに置きます。
- **Construction に入る前の準備（2点）**: (1) 現在 `main` にはコミットが1つもないため、Bolt 1 の worktree を切る前に `aidlc/`・`.claude/`・`.gitignore` を初回コミットします。(2) その初回コミットの前に `.gitignore` へ `.env`、`.env.*`、鍵ファイル（`*.pem`、`*.keystore`、`*.jks` など。スタック決定後に判明する秘密ファイルの拡張子も含む）を追加します。一度コミットした秘密情報は squash しても履歴に残るため、最初の1回が肝心です。
- 複数環境（staging / production）はこのワークフローには存在しません。将来公開する場合も、長期のリリースブランチではなくタグや環境別の設定で切り替えます。

## Walking Skeleton

- 選択中のスコープ `fishing-app-greenfield` は `skeleton: on` を宣言しているので、Construction の Bolt 1 は**ウォーキングスケルトン**（端から端まで最小限つながった版）として、単独で・承認ゲート付きで実行します。本人が Bolt 1 を明示的に承認してから残りの Bolt が動きます。
- Bolt 1 の一本通しは **「釣果を1件登録すると一覧に出る（写真なし・文字だけ）」** です。スマホの画面で動く、保存される、一覧に出る、の3点が最初につながることを確認します。写真の撮影・表示はスケルトンに含めず、PU-1 本体の Bolt で足します。
- Bolt 1 の完了条件には、機能の一本通しに加えて次を含めます: (a) リポジトリ直下に「整形チェック → リント → ビルド → テスト（カバレッジ出力付き）」を1コマンドで実行する入口があり、緑であること。(b) フォーマッタとリンタの設定ファイルがリポジトリ直下にあること。(c) 各層に正常系のテストが最低1本あること（スケルトンでは Standard 戦略の本数を満たす必要はなく、PU-1 本体の Bolt で満たします）。
- Bolt 1 が終わると「残りの Bolt をどう進めるか」（自律的に続ける／毎 Bolt でゲートする）を尋ねられます。選んだ結果は `aidlc-state.md` の `Construction Autonomy Mode` に記録されます。

## Testing Posture

テストは各 Bolt の成果物の一部として扱います。方法論と順序は次の2項目で明示し、Code Generation はこの2項目をカバレッジ・ツール・スコープ注記とは独立に読み取ります。

- **Methodology**: test-after
- **Ordering**: ロジック → 保存 → 画面 の順に、層を1つ実装するごとにその層のテストを書いて通し、緑になってから次の層に進む。

層の定義（どのスタックでも同じ3層）:

- **ロジック層** — 釣果1件の入力検証（サイズ・重さが数値か、必須項目が揃っているか）、一覧の並び順（新しい順）、表示の整形。外部依存なし。単体テストで検証します。
- **保存層** — 釣果を保存する／一覧を読み出す／写真の参照を保持する。メモリ内または一時ディレクトリの実ストアを使った結合テストで検証します（アプリ再起動後も残ることを含む）。
- **画面層** — S1（空の状態・一覧）、S2（入力エラー文言・保存中・保存後に S1 の先頭へ）、S3（未入力項目を出さない）。スタックの画面コンポーネントテストで検証します。

カバレッジ・量・ゲート:

- **カバレッジの床**: ロジック層と保存層は**行カバレッジ 80% 以上**を必須とします。画面層は計測して結果を残しますが、数値の下限は設けません。この床は Build and Test で確認され、通すために弱めることはできません。
- **テストの量**: このワークフローの `Test Strategy` は `Standard`（1コンポーネントあたり単体＋結合で 5〜8 本、自動 E2E なし）です。PU-1 のコンポーネントは釣果モデル／検証・保存・S1・S2・S3 の5つ程度なので、目安は 25〜40 本です。スコープごとの床は加算されるだけで、この設定を弱めることはありません。
- **マージ前ゲート（CI ができるまで）**: ci-pipeline ステージは build-and-test の後に実行されるため、Bolt 1 と PU-1 本体のマージ時には CI がありません。それまでは、リポジトリ直下の1コマンド（整形チェック → リント → ビルド → テスト）を手元で実行して緑になったものだけを `main` に取り込みます（暫定ゲート）。
- **CI 移行後**: ci-pipeline ステージでは、その同じ1コマンドを CI が呼ぶだけにします。手元と CI で実行内容が同一になり、「手元では通るのに CI で落ちる」を構造的に防ぎます。CI が緑であることがマージ条件になります。
- **各 Bolt の最低ライン**: テストは正常系に加えて異常系・境界を2つ以上含めます。必ず成功するだけのテスト（実装に関わらず通るもの）は書きません。落ちたテストを再実行して緑にする（retry-to-green）ことで済ませず、原因を直します。
- **回帰**: 既存のテストは常に緑を保ちます。端末で見つけた不具合は、自動化できるものなら直す前に再現テストを1本書きます。
- **端末での手動チェックリスト（推奨）**: Standard には自動 E2E がなく、成功条件が「本人のスマホで動く」なので、PU-1 の Bolt 完了時に本人のスマホで次を確認することを推奨します: 初回起動で空の状態が出る／登録できる／一覧が新しい順／アプリを完全終了して再起動しても残っている／写真の代替テキストとタップ領域。電波のない場所（機内モード）での動作確認は固定ルールにはしていませんが、釣り場に電波がない可能性があるため確認項目に加えることを推奨します。
- **テストデータ**: テストのフィクスチャや画面のサンプルには架空の写真・架空の座標・架空の名前を使うことを推奨します（友達の実データがリポジトリに残るのを防ぐため。固定ルールではありません）。
- **ツールの種類（スタック中立の要件、domain-design に引き継ぐ）**: (1) テストランナーと、全テスト＋リント＋ビルドを走らせる1コマンドの入口。(2) カバレッジを機械可読の形式（lcov / Cobertura / JSON 等）で出力でき、ディレクトリ単位で閾値を分けられること（層別の床の前提）。(3) 保存層のフェイク（メモリ内または一時ディレクトリの実ストア）。(4) 画面コンポーネントのテストハーネス（スタック標準のもの）。(5) 注入できる時計（登録日時を自動記録する前提のため、時刻を差し替えられないと日付依存のテストになる）。(6) 釣果1件のテストデータ生成ヘルパー。(7) テストコードもリンタ・フォーマッタの対象にする。製品名は domain-design で決めます。

## Deployment

- **今回の配布先は開発者本人のスマホ1台**です。公開（サーバーやストアへの配置、友達が各自の端末から使える状態にすること）は intent-statement / scope-document で範囲外と決まっており、Operation フェーズの全ステージは SKIP です。staging / production の環境はありません。
- **「載せてよい」の判定**: `main` が緑（CI ができるまでは上記の暫定ゲート、CI 移行後は CI）であることを「配布可能な状態」とみなします。毎コミットがリリース候補、という考え方を最小限で守ります。
- **「緑」の定義**: 整形チェック・リント（セキュリティ系ルールセットがあれば有効化）・ビルド・テスト（カバレッジの床を含む）に加えて、CI 移行後は次の2つを含めます。(1) **シークレット検出**（リポジトリをキー・トークン・秘密鍵のパターンで走査。検出したらブロック）。(2) **依存関係の脆弱性監査**（選んだパッケージマネージャの組み込み監査コマンド。修正版がある Critical／High はブロック、それ以外は警告）。DAST・コンテナ／IaC スキャン・別立ての SAST サーバは、公開環境も対象物もないため今回は入れません。
- **載せ方の手順書**: 自分のスマホへ載せる手順（ビルド方法、端末への転送・起動方法）を、スタック決定後に `README` などに再現できる手順書として残します。外部サービスのキーが必要になった場合は、キーをソースやビルド成果物に埋め込まず、環境変数またはビルド時設定から渡す旨を手順書に書きます。
- **ロールバック**: 不具合時は「1つ前の緑の状態（`main` の1つ前の緑コミット）を再ビルドして載せ直す」ことをロールバック手順とします。ロックファイルをコミットし CI がロックファイルどおりにインストールすることで、同じコミットが同じ依存で再現ビルドできることがこの手順の前提です。
- **将来の公開**: 友達各自の端末で使えるようにする段階は別のインテント（`infra` スコープ相当）で扱い、その時点で staging の要否や production の承認方法を改めて決めます。

## Code Style

- **フォーマッタとリンタは必須**です。domain-design で言語・フレームワークが決まったら、その言語の標準的なフォーマッタとリンタ（言語既定のもの）を採用し、設定ファイルをリポジトリ直下に置きます。リンタにセキュリティ系のルールセットがあれば有効にします（今回の SAST はこれで十分です）。製品名と設定値（行幅、インデント幅など）はこの工程では決めません。
- **違反は取り込み不可**: 整形チェックとリントはマージ前ゲート（暫定ゲート、CI 移行後は CI）に含め、失敗したら `main` に取り込めません。開発者が1人でもこのゲートは外しません。エディタの保存時自動フォーマットを併用することを推奨します。
- **命名**: その言語の慣習（camelCase / snake_case / PascalCase など）に従います。リンタが拾わない範囲の推奨: 関数名は動詞＋名詞（例: `saveCatch`、`listCatches`）、真偽値は `is` / `has` 接頭辞、真の定数は大文字スネークケース、略語は広く通じるもの（`id`、`url`）以外は使わない。
- **言語**: コードの識別子（変数名・関数名・ファイル名）は**英語**。コメントとコミットメッセージは**日本語で可**。画面に出る文言は日本語です。
- **ドメイン用語の英語対応表**: 「釣果」「魚種」「釣り場」「釣行」など、画面では日本語・コードでは英語になる言葉の1対1の対応表を domain-design で1回だけ作り、命名の揺れを防ぎます。これ以外のプロジェクト固有の命名ルールは今は追加しません。
- **画面文言は1か所にまとめる**: ボタン名・エラー文言を各画面にハードコードせず、文言ファイル（または定数モジュール）1つに集めます。i18n の仕組みは不要です。
- **レイヤ境界（推奨）**: 「画面（UI）／ロジック（釣果の型・入力検証・並び順）／保存」の3層に分け、依存の向きは「画面 → ロジック ← 保存」とします。画面が保存層を直接呼ばないことを推奨します（後で友達との共有＝サーバー同期を足すときに画面を直さずに済むため）。固定ルールではありませんが、Code Generation はこの向きを既定として扱います。保存が1種類（ローカル）の間は Repository の抽象インタフェースは切らず、保存層を1モジュールに閉じ込めるだけにします。
- **エラー処理（推奨）**: 保存層の I/O 失敗は「保存できなかった」「読み込めなかった」として画面に返し、画面は wireframes の文言（S1「釣果を読み込めませんでした [再読み込み]」、S2「保存できませんでした。もう一度お試しください」、入力内容は保持）を出します。`catch` して何もしない、は行いません（少なくともログに出すか呼び出し元に返す）。入力検証は画面→ロジックの境界で1回だけ行います。回復可能（再読み込み・再試行）と致命的（保存領域の初期化失敗など）を区別し、致命的なものは起動時に fail-fast で気づけるようにします。例外か Result 型かといった具体的な仕組みは選んだスタックのイディオムに従います。
- **ファイル構成（推奨）**: 技術層別（`models/` `services/` `views/`）に散らさず、機能単位でまとめます（PU-1 は `catches/` 1つ、PU-2 で `groups/`、PU-4 で `spots/` を足す形）。フレームワークが雛形の階層を決めている場合はその直下でこの方針を適用します。1ファイル1概念とし、300 行を超えたら分割の合図とします。テストの置き場所はスタックの標準に従います。
- **依存関係の固定**: ロックファイル（スタック相当の `package-lock.json` / `poetry.lock` / `Cargo.lock` / `pubspec.lock` など）は必ずコミットし、CI はロックファイルどおりにインストールします（frozen / ci 相当のモード）。依存関係の自動更新（Dependabot / Renovate 相当）は、ホスティング先が対応していればセキュリティ更新のみ・月1回まとめで有効化します（釣行後でも可）。
- **型注釈の厳しさ**: スタックが用意する最も厳しい既定を初期値にします（後から厳しくするほうが高くつくため）。具体値はスタック決定時に決めます。
- **フレームワークからの提案の優先順位**: エージェントがコードスタイルを提案するときは、まずプロジェクトのリンタ設定を読み、リンタが既にカバーしている項目については提案しません。
