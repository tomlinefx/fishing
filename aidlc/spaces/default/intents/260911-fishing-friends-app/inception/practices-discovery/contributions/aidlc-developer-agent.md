## Contribution

> 観点: 命名、レイヤ境界、エラー処理、ファイル構成、コードスタイル規約。ワークスペースはグリーンフィールド（コード・CI・テスト・パッケージ定義なし、`main` にコミット0件）なので、既存コードから推論できる慣習はありません。以下はリードドラフト `team-practices.md` の Code Style 節と Way of Working 節への評価と、スタックが未定（domain-design で決定）でも今 affirm してよい**スタック中立の原則**、そして逆に**スタック決定前に決めてはいけないこと**の切り分けです。インタビューで本人に聞くべき質問は末尾にまとめました。

### 1. Code Style 節の評価

ドラフトの骨子（フォーマッタ／リンタはスタックの標準に従う、CI でブロック、命名は言語の慣習、リンタが既にカバーする項目は提案しない、画面文言は日本語）は妥当で、org.md の既定値と矛盾しません。補うべき点は次の4つです。

1. **「フォーマッタ＋リンタは交渉不可」と明文化する** — 開発者1人・期限ありの状況では「後で入れる」誘惑が最も強く、後から入れると差分が全ファイルに及びます。Bolt 1（ウォーキングスケルトン）の完了条件に「フォーマッタとリンタの設定ファイルがリポジトリ直下にあり、CI で実行されている」を含めることを提案します。合否判定: 設定ファイルの存在と CI ジョブの実行ログ。
2. **識別子の言語は英語を推奨し、コメント・コミットメッセージは日本語でよい** — ほぼすべてのリンタ、フレームワークの雛形、ライブラリ、エラーメッセージが英語識別子を前提にしており、日本語識別子は言語によっては不可、可能でも IDE 補完や検索と相性が悪いためです。ドラフトはこの点を「インタビューで確認」としており、それでよいのですが、推奨案を添えて聞くべきです。
3. **ドメイン用語の英語対応表を domain-design で1回だけ作る** — 「釣果」「魚種」「場所（釣り場）」「釣行」など、画面では日本語・コードでは英語になる言葉を1対1で固定します（例: 釣果→`catch`、魚種→`species`、釣り場→`spot`）。ドラフトの「プロジェクト固有の命名ルールは今は追加しない」には賛成ですが、この対応表だけは例外として、命名の揺れ（`fish` / `catch` / `record` の混在など）を最初から防ぐ価値があります。
4. **画面文言は1か所にまとめる** — 画面の文言が日本語であることは wireframes から確定しています。i18n の仕組みは不要ですが、ボタン名・エラー文言を各画面にハードコードして散らさず、文言ファイル（または定数モジュール）1つに集めます。合否判定: 画面コードの中に日本語リテラルが直接書かれていない。

### 2. Way of Working 節の評価

- **トランクベース＋squash-merge** — 賛成。フレームワークの worktree ツールの既定値と一致し、追加設定なしで動きます。開発者1人なら squash で中間コミットが消えることの不利益はありません。
- **ソロ変種「Bolt 外の小さな修正は `main` に直接コミット」** — 方向は賛成ですが、ドラフトの「README、設定の微調整」という範囲は曖昧です。**「アプリのソースコードとテストに触らない変更（README、`aidlc/` の記録、CI 設定の微修正）に限る」**と定義してほしい。理由: 直接コミットがアプリコードに及ぶと、Deployment 節の「CI 緑＝配布可能」の判定と「1つ前の緑コミットに戻す」ロールバック手順が成り立たなくなります。合否判定: `main` への直接コミットの差分にアプリのソース／テストのパスが含まれない。
- **ブランチ命名** — Bolt ブランチ `bolt-<slug>` はフレームワークが生成するので決める余地はありません。本人が手でブランチを切る場面はほぼ無いはずですが、切る場合は kebab-case で、`bolt-` 接頭辞は使わない（フレームワークの worktree と衝突させない）ことだけ決めれば十分です。
- **コミット粒度** — Bolt ブランチ内のコミットは squash で消えるため、粒度に厳格なルールは不要です。squash 後に `main` に残る1コミットのメッセージは `<bolt-slug>: <1行要約>` の形に固定することを提案します（監査ログと突き合わせやすい）。Conventional Commits の強制は、1人開発で得るものが少ないので不要です。メッセージの言語（日本語／英語）はインタビューで確認します。
- **初回コミットの前提条件** — 賛成。Construction に入る前に `aidlc/` と `.claude/`、`.gitignore` を初回コミットしないと Bolt 1 の worktree を切れません。

### 3. スタック中立で今 affirm してよい規約

以下は言語・フレームワークが何であっても同じ形で適用でき、かつ PU-1 の後に PU-2〜PU-3（グループ・タイムライン共有）でストレージがローカルからサーバー同期に変わる可能性が高いことから、**今決めておくと後の手戻りを防げる**原則です。

**レイヤ境界（小さなアプリ向けの3層）**

| 層 | 責務 | 知ってよいもの | 知ってはいけないもの |
|---|---|---|---|
| 画面（UI） | 表示、入力の受け取り、文言の表示 | ドメイン層 | 保存の仕組み（DB、ファイル、API） |
| ドメイン／データ | 釣果の型定義、入力検証（サイズは数値、など）、並び順（新しい順） | なし（自己完結） | 画面、保存の仕組み |
| 保存（ストレージ） | 保存と読み出し。ドメインの型を受け取り、ドメインの型を返す | ドメイン層 | 画面 |

- 依存の向きは「画面 → ドメイン ← 保存」。**画面が保存層を直接呼ばない**ことが唯一の禁止事項です。合否判定: 画面のファイルからストレージ層のモジュールへの import／参照がない。
- 3層より増やしません。保存が1種類（ローカル）の間は Repository の抽象インタフェースも不要で、保存層を1ファイル（または1モジュール）に閉じ込めるだけで足ります（`code-generation-guide` の「Repository: 単一 DB・単純 CRUD のみなら避ける」に従う）。サーバー同期が実際に来た時点で差し替えます。
- ドラフトの Testing Posture の Ordering「テスト可能な層を1つ実装するごとに」と整合します。最も単体テストしやすいのはドメイン層なので、Bolt 1 ではドメイン層のテストから書くのが自然です。

**エラー処理（境界で処理し、握りつぶさない）**

- 保存層の I/O 失敗は「保存できなかった」「読み込めなかった」として呼び出し元（画面）に返し、画面が wireframes の文言（S1「釣果を読み込めませんでした [再読み込み]」、S2「保存できませんでした。もう一度お試しください」、入力内容は保持）を出します。
- `catch` して何もしない、は禁止。少なくともログに出すか呼び出し元に返す。
- 入力検証は画面→ドメインの境界で1回（S2 の「保存する」時点）だけ行い、以後の層で再検証しません。
- 回復可能（再読み込み、再試行）と致命的（保存領域の初期化失敗など）を区別し、致命的なものは起動時に fail-fast で気づけるようにします。
- 例外にするか Result 型にするかといった**具体的な仕組みは選んだスタックのイディオムに従う**ため、今は決めません。

**ファイル構成（機能単位）**

- 技術層別（`models/` `services/` `views/`）に散らさず、機能単位でまとめます。PU-1 は `catches/`（釣果）1つで完結し、PU-2 で `groups/`、PU-4 で `spots/` を足す形です。フレームワークが雛形の階層（`src/`、`lib/`、`app/` など）を決めている場合はその直下でこの方針を適用します。
- 1ファイル1概念。1ファイルが 300 行を超えたら分割の合図とします（合否判定が明確な閾値として）。
- テストはスタックの標準的な置き場所（ソースの隣、または `test/` 相当）に従います。
- 画面文言は上記のとおり1か所。

**命名（リンタが拾わない範囲だけ）**

- スタックの慣習（camelCase / snake_case / PascalCase）に従う — ここはリンタが拾うので規約として書く必要はありません。
- リンタが拾わない範囲として、関数名は「動詞＋名詞」（`saveCatch`、`listCatches`）、真偽値は `is` / `has` 接頭辞、真の定数は大文字スネークケース、略語は広く通じるもの（`id`、`url`）以外は使わない、を team.md の Code Style に1行で残す価値があります。
- ドメイン用語の英語対応表は上記 1-3 のとおり domain-design で確定します。

### 4. スタック決定前に決めてはいけないこと

以下を practices-discovery で決め打ちすると、domain-design での選択肢を不当に狭めるか、選んだスタックの既定と衝突します。

- フォーマッタ／リンタの**製品名**と**設定値**（行幅、インデント幅、引用符の種類など）。
- エラーの表現（例外か Result 型か）。
- ディレクトリの具体名（`src/` か `lib/` か `app/` か）とテストファイルの配置。フレームワークの雛形に従う。
- import／モジュールの書き方（named／default、絶対／相対）。
- 型注釈の厳しさ（TypeScript の `strict` など）。決めるのはスタック決定時ですが、「スタックが用意する最も厳しい既定を初期値にする」とだけ提案しておきます（後から厳しくするほうが高くつくため）。
- 保存層の抽象の形（インタフェースを切るか、同期の仕組み）。domain-design の永続化の決定を待つ。
- CI の具体的なジョブ定義（実行コマンド）。ci-pipeline で具体化。

### 5. インタビューで本人に聞くべき質問（簡潔に答えられる形）

Code Style:

1. コードの識別子（変数名・関数名・ファイル名）は英語でよいですか？ コメントとコミットメッセージは日本語でよいですか？（推奨: 識別子は英語、コメント・コミットは日本語）
2. フォーマッタとリンタを最初の Bolt で必ず入れ、CI で失敗したらマージできない、でよいですか？（推奨: はい。1人でも外さない）
3. エディタの保存時自動フォーマットも使いますか、それとも CI だけで検査しますか？（推奨: 両方。保存時フォーマットで CI 失敗の往復を減らす）
4. 画面に出す日本語の文言は、画面ごとに書かず1つのファイルにまとめる、でよいですか？（推奨: はい）

Way of Working:

5. `main` への直接コミットを許す範囲は「アプリのコードとテストに触らない変更（README、`aidlc/` の記録、CI 設定）だけ」でよいですか、それとも一切許しませんか？（推奨: 触らない変更だけ許す）
6. squash 後に `main` に残るコミットメッセージは `<bolt-slug>: 1行要約` の形でよいですか？（推奨: はい）

レイヤ境界・エラー処理:

7. 「画面／釣果のデータと検証／保存」の3つに分け、画面が保存を直接呼ばない、という境界を守ることに同意しますか？ 後で友達との共有（サーバー同期）を足すときに画面を直さずに済むための線です。（推奨: はい）
8. 保存や読み込みの失敗は、黙って失敗させず必ず画面に文言で出す、でよいですか？（推奨: はい。wireframes の文言をそのまま使う）

これらの質問は、`discovered-rules.md` の `## Mandated` / `## Forbidden` に入れる候補（本人が「必ず」「絶対に」と答えた場合のみ）としては 2・7・8 が該当しうるものです。それ以外は team.md の Code Style / Way of Working の本文に留めるのが適切です。

## Positions

- AGREE: トランクベース開発＋Bolt ブランチの squash-merge — org.md の既定値およびフレームワークの worktree ツールの既定フラグと一致し、開発者1人なら中間コミットを失う不利益もない。
- AGREE: フォーマッタ／リンタはスタックの標準に従い、製品名をこの工程で決めない — スタックは domain-design で決まるため、今決めると選択肢を不当に狭める。
- AGREE: リンタ／フォーマッタの検査を CI で実行し、失敗したらマージをブロック。1人でも外さない — 後から入れると全ファイルに差分が及ぶため、最初から入れる以外に安価な方法がない。
- AGREE: 命名は言語の慣習に従い、プロジェクト固有の命名ルールは今は追加しない — ただし「ドメイン用語の英語対応表を domain-design で1回作る」だけは例外として明記してほしい（Contribution 1-3）。

- OBJECT: ソロ変種「Bolt 外の小さな修正（README、設定の微調整）は `main` に直接コミット」の範囲が曖昧 — 「アプリのソースコードとテストに触らない変更に限る」と定義しないと、Deployment 節の「CI 緑＝配布可能」判定と「1つ前の緑コミットへ戻す」ロールバック手順が直接コミットで崩れる。
