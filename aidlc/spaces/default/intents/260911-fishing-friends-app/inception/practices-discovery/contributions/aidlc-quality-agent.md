### 2. `Ordering` に明示すべき3層（スタック中立）

Code Generation が `Ordering` を独立に読み取るため、「層」が何を指すかを1文で固定しておくほうがよい。PU-1（釣果の登録と一覧）を構成する層は、どのスタックでも次の3つに分かれる。

1. **ロジックの層** — 釣果1件の入力検証（サイズ・重さが数値か、必須項目が揃っているか）、一覧の並び順（新しい順）、表示の整形（`25cm / 120g`、未入力項目の行を出さない）。外部依存なし。**単体テスト**で数ミリ秒。
2. **保存の層** — 釣果を保存する／一覧を読み出す／写真の参照を保持する。**結合テスト**（メモリ内または一時ファイルの実ストアを使う）。
3. **画面の層** — S1（空の状態・一覧）、S2（入力エラー文言・保存中・保存後に S1 の先頭へ）、S3（未入力項目を出さない）。スタックの**画面コンポーネントテスト**（ピラミッド上は結合テスト扱い）。

提案する `Ordering` の文: **「ロジックの層 → 保存の層 → 画面の層の順に、1層を実装するごとにその層のテストを書いて実行し、緑になってから次の層に進む。」**

### 3. カバレッジの床 — インタビューに出すべき選択肢

一度決めた床は Build and Test で確認され、通すために弱められない（org.md）。だから**最初は守れる床**を選び、後で引き上げるほうが安全。

- **A（推奨）: ロジックの層と保存の層に行カバレッジ 80%、画面の層は測るだけ。** 主要なテストランナーは、ディレクトリやファイルパターン単位で閾値を分けられる（スタック中立に実現できる）。画面コードの1行1行を追うコストを避けつつ、壊れると釣行当日に困る「保存される／並ぶ／検証される」部分には実質的な床が残る。
- **B: コード全体に 80%。** org.md の mvp / feature 相当。画面コードのテストに時間を取られ、期限との相性が悪い。
- **C: 測るだけで床なし。** 数値は CI の出力に残す。期限最優先ならあり得るが、「テストは一級の成果物」という org.md の方針との整合が弱い。
- 補足: 床の対象は**行カバレッジ**でよい（分岐カバレッジは趣味アプリには過剰）。

### 4. CI が存在しない期間の「マージ前ゲート」の定義

ci-pipeline ステージは build-and-test の**後**に実行される。よって Bolt 1 と PU-1 本体のマージ時には CI がない。次の2段構えを提案する。

1. **暫定ゲート（CI ができるまで）**: リポジトリ直下に**1コマンドで lint → build → test（＋カバレッジ出力）をすべて実行する入口**（スタック標準のスクリプト／タスクランナーの1ターゲット）を置き、Bolt のマージ前にそれをローカルで実行して緑であることをマージ条件にする。ウォーキングスケルトン（Bolt 1）の完了条件に「この1コマンドが存在して緑」を含める。
2. **CI 移行後**: ci-pipeline ステージでは、その**同じ1コマンド**を CI が呼ぶだけにする。ローカルと CI で実行内容が同一になり、「ローカルでは通るのに CI で落ちる」を構造的に防げる。

前提としてインタビューで**リモートリポジトリ（GitHub 等）を Construction 前に用意するか**を確認する必要がある。リモートがなければ「CI」は当面ローカルの1コマンド（必要なら pre-push フック）が実体になる。

### 5. Standard 戦略で意味のあるテストの種類（小さなスマホ向け趣味アプリ）

Standard は「1コンポーネントあたり 5〜8 本、単体＋結合」（testing-guide.md）。PU-1 のコンポーネントは、釣果モデル／検証・保存・S1・S2・S3 の**5つ程度**なので、目安は **25〜40 本**。ただし**スケルトン Bolt では「1層に正常系1本＋端末チェックリスト」を床**とし、5〜8 本は PU-1 本体を埋める Bolt で満たす（スケルトンで満数を要求すると「薄い一本通し」の目的に反する）。

| 種類 | 対象 | 判定 |
|---|---|---|
| 単体テスト | ロジックの層（検証・並び順・整形） | **必須**。全体の大半をここに置く。 |
| 結合テスト（保存） | 保存 → 読み出し → 新しい順、写真参照の保持、**アプリを再起動しても残る** | **必須**。「保存される」は釣行当日の成功条件そのもの。 |
| 画面コンポーネントテスト | S1 空状態／一覧、S2 入力エラー文言と保存後の遷移、S3 未入力行の非表示 | **必須（画面ごとに正常系1本＋エラー/境界2本）**。wireframes の「その他の状態」がそのままテストケース一覧になる。 |
| 自動 E2E | — | **不要**。Standard の範囲外で、端末上の自動化はスタック依存で高い。代わりに下の手動チェックリスト。 |
| 手動の端末チェックリスト | 本人のスマホ1台 | **PU-1 の Bolt 完了条件に含めることを推奨**（ドラフトのインタビュー項目に賛成）。項目案: (1) 初回起動で空の状態が出る、(2) カメラで撮って登録できる、(3) 写真なしで登録できる（必須項目の決定次第）、(4) 一覧が新しい順、(5) **アプリを完全終了して再起動しても残っている**、(6) **機内モードで登録・一覧が動く**（釣り場に電波がない可能性）、(7) 写真の代替テキストとタップ領域（wireframes のアクセシビリティ項目）。 |
| 性能・負荷テスト | — | **不要**。NFR ステージは SKIP、利用者は本人と友達数名。 |
| セキュリティテスト | — | テスト戦略としては要求しない（依存関係スキャン等は devsecops の領分）。 |
| 不具合の再現テスト | 端末チェックリストで見つけた不具合 | 自動化できるものは**直す前に再現テストを1本**書く（quality の原則「Every defect gets a test」）。 |

### 6. スタックに関係なく要求する「ツールの種類」

domain-design で製品名を決めるときの**必須要件**として次を残しておくと、選定が楽になる。

1. **テストランナー**と、全テスト＋lint＋build を走らせる**1コマンドの入口**（4. と同じもの）。
2. **カバレッジ計測**が機械可読の形式（lcov / Cobertura / JSON 等）で出力でき、**ディレクトリ単位で閾値を分けられる**こと（3. の A 案の前提）。
3. **保存層のフェイク**（メモリ内または一時ディレクトリの実ストア）。単体テストが端末の実ストレージに触れない。
4. **画面コンポーネントのテストハーネス**（スタックが標準で提供するもの）。
5. **注入できる時計**。「登録日時をアプリが自動で記録する」前提（scope-document / wireframes の assumption）があるため、時刻を差し替えられないとテストが日付依存になる。
6. **釣果1件のテストデータ生成ヘルパー**（有効な1件を既定値で作り、必要な項目だけ上書きする）。固定データのコピペを防ぐ。
7. テストコードも**リンタ・フォーマッタの対象**にする。

### 7. インタビューで本人に確認すべき質問（テスト観点）

いずれも短く答えられる形にしている。既定案は先頭。

- **T1. テストを書く順番**: 実装した後に書く（既定） / 先にテストを書く / 振る舞いの筋書きを先に書く / 混在。
- **T2. カバレッジの床**: A ロジック＋保存に 80%、画面は測るだけ（推奨） / B 全体に 80% / C 測るだけ / D 別の数値。
- **T3. CI ができるまでのマージ条件**: 「1コマンドで lint・build・test をローカル実行して緑」をマージ条件にする（推奨） / CI ができるまではゲートなし。あわせて **GitHub 等のリモートを Construction 前に用意するか**（はい / いいえ / 未定）。
- **T4. スマホでの手動チェックリスト**: PU-1 の完了条件に含める（推奨、項目は 5. の案） / 含めず自動テストのみ。
- **T5. 電波のない釣り場**: 次の釣行先で電波がない可能性はあるか（ある / ない / わからない）。「ある」なら機内モード確認をチェックリストに入れ、設計（ローカル保存前提）にも伝える。
- **T6. 写真の扱い**: 釣行当日はカメラ撮影が必須か、端末の写真から選べれば十分か。カメラ経路は自動テスト不可なので、必須なら手動確認の項目として固定する。
- **T7. テストの説明文の言語**: テストの名前・説明文は日本語（推奨。「釣果を保存すると一覧の先頭に出る」のように読める） / 英語。※コード上の識別子の言語（リードの Code Style 質問）とは分けて答えられるようにする。

## Positions

- AGREE: `Methodology: test-after` を既定にして選び直せる形にしたこと — 1人・短期限・スタック未定では、先にテストを書く方法論の学習コストが期限を圧迫する。
- AGREE: 「CI 緑は必須、数値の床は本人判断」という切り分け — カスタムスコープは org.md の 80% 対象一覧に含まれず、自動適用されないという読みは正しい。
- AGREE: 端末での手動チェックリストをインタビューに出したこと — Standard には自動 E2E がなく、成功条件が「本人のスマホで動く」である以上、手動確認が唯一の一本通し検証になる。
- AGREE: ツールの製品名を domain-design まで決めないこと — ただし「ツールの種類」の要件は今決めて引き継ぐべき（Contribution 6.）。
- OBJECT: 「マージ前に CI で緑」を Bolt の必須条件と書いている点 — このスコープでは ci-pipeline が build-and-test の後に来るため、Bolt 1 と PU-1 本体のマージ時に CI は存在しない。CI ができるまでの暫定ゲート（1コマンドをローカル実行して緑）を定義し、スケルトンの完了条件にその1コマンドを含める必要がある。
- OBJECT: カバレッジの床の質問が「全体に 80% か、測るだけか」の二択になっている点 — 画面コードの網羅は高くつくため「測るだけ」に流れやすい。「ロジック＋保存に 80%、画面は測るだけ」の層別の床を第3の選択肢として提示すべき。
- OBJECT: `Ordering` の「層」の例示にロジックの層（入力検証・並び順・表示整形）が無い点 — いちばん安く価値の高い単体テスト対象が抜けると、テストが保存層と画面層に偏りピラミッドが崩れる。3層を明示し順序も固定すべき。
- OBJECT: 「登録日時を自動記録する」前提に対するテスト上の手当てが無い点 — 時計を注入できないと日付依存のテストになる。注入できる時計とテストデータ生成ヘルパーをツール要件に加えるべき。
