### 1. リード draft の評価（セキュリティパイプラインの観点）

**Code Style（同意、追記1点）**
- 「選んだスタックの標準フォーマッタ／リンタに従い、マージ前 CI でブロック、ひとりでも外さない」は妥当です。セキュリティ観点でも、静的解析の第一段はリンタなので、ここが土台になります。
- 追記提案: リンタに**セキュリティ系のルールセットがあるなら有効にする**（例: JS/TS なら ESLint のセキュリティ系プラグイン、Python なら Ruff の `S` 系ルール、Go なら `gosec` 相当。製品名は domain-design 後に決める）。これが今回の「SAST」の全部で十分です。SonarQube や CodeGuru のような別立ての SAST サーバは趣味アプリには過剰です。

**Way of Working（おおむね同意、条件1点）**
- トランクベース・squash-merge は問題ありません。
- 「Bolt 外の小さな修正は `main` に直接コミットしてよい」を許すなら、**直接コミットにも CI（少なくともシークレット検出とリンタ）が走る**ことを条件にしてください。draft では CI が「マージ前」にだけ走る書き方になっており、直接コミットは CI を素通りします。実際に `.env` やキーが漏れる経路は、たいてい「ちょっとした設定の修正」の直接コミットです。
- 「Construction 前に初回コミットを行う」に同意しますが、**初回コミットの前に `.gitignore` に `.env` / `.env.*` と、スタック決定後に判明する鍵ファイルの拡張子を追加する**ことを前提条件に加えてください（今の `.gitignore` にはありません）。一度コミットしたシークレットは squash しても履歴に残るため、最初の1回が肝心です。
- `aidlc/` の記録（監査シャード・成果物）はコミットされます。フレームワークの監査規約どおり「機密・個人情報を書かない」を守るため、以後の成果物やテスト資料に**友達の実名・実際の座標・実際の写真**を貼らない運用にしてください（後述の候補ルール2と同じ趣旨）。

**Deployment（同意、定義に2項目追加）**
- 「今回の配布先は本人のスマホ1台」「CI 緑＝配布可能」「1つ前の緑コミットに戻す」という縮約は妥当です。DAST（動いているアプリへの攻撃的スキャン）は、公開環境がないので**今回は対象外**でよいです。コンテナ／IaC のスキャンも、コンテナもインフラも作らないので不要です。
- ただし「CI 緑」の定義が draft では lint / build / test だけです。次の2つを「緑」の定義に含めることを提案します（どちらも数分で入り、日常的には何も出ません）:
  1. **シークレット検出**（後述 2-1）
  2. **依存関係の脆弱性監査**（後述 2-2）
- スマホに載せる手順を README に残す点に補足: 地図（PU-4／PU-5）や、将来の共有機能で外部サービスのキーが要るようになったとき、**キーをアプリ本体（ソースやビルド成果物）に埋め込まない**方針を、手順書に「キーは環境変数／ビルド時設定から渡す」と一行書いておくと、後で公開するときにやり直しが減ります。今回（PU-1、端末内のみ）はキーが要らない可能性が高いので、必須ではなく注記です。

**Testing Posture（自分の視点からの補足1点）**
- テストの方法論・順序には意見しません。ひとつだけ: テストデータ（フィクスチャ）や画面のサンプルには**架空の写真・架空の座標・架空の名前**を使う、をテストの作法に含めてください。理由は品質ではなくデータ保護です（友達の実データがリポジトリに残るのを防ぐ）。

### 2. 趣味アプリに釣り合う最小の CI セキュリティゲート

| # | ゲート | 内容（スタック中立） | 失敗時 | 理由 |
|---|---|---|---|---|
| 2-1 | シークレット検出 | リポジトリ全体をキー・トークン・秘密鍵のパターンで走査する（Gitleaks のような単体ツール、またはホスティング先の組み込み機能）。`main` への push と PR の両方で実行 | **ブロック** | 最も安く、最も取り返しがつかない事故を防ぐ。誤検知は除外設定で対応できる |
| 2-2 | 依存関係の脆弱性監査 | 選んだパッケージマネージャの**組み込みの監査コマンド**（npm / pip / cargo / pub などの audit 相当）を CI で実行 | **修正版がある Critical／High はブロック、それ以外は警告** | 「修正版のない推移的依存の CVE」で釣行前の作業が止まるのは本末転倒。修正できるものだけ止める |
| 2-3 | リンタ＋フォーマッタ | draft のとおり。セキュリティ系ルールセットがあれば有効化 | ブロック | 今回の SAST はこれで十分 |
| 2-4 | ロックファイルの固定 | ロックファイル（`package-lock.json` / `poetry.lock` / `Cargo.lock` / `pubspec.lock` など、スタック相当）を**必ずコミット**し、CI は「ロックファイルどおりに」インストールする（frozen／ci 相当のモード） | ブロック（インストールが失敗するだけ） | サプライチェーンの最低限。同じコミットが同じ依存で再現ビルドできる＝「1つ前の緑コミットに戻す」が成り立つ前提 |
| 2-5 | 依存関係の自動更新 | ホスティング先が対応していれば Dependabot／Renovate 相当を**セキュリティ更新のみ・月1回まとめ**で有効化 | 通知のみ | ひとりだと更新 PR が雑音になりやすい。釣行後に有効化でもよい |

**任意（あれば良いが必須にしない）**
- pre-commit フック（コミット時のシークレット検出）。ひとりなら入れやすいが、CI 側（2-1）があれば省略可。
- CI の外部アクション／プラグインのバージョン固定（メジャータグまで）。コミットハッシュまで固定するのは趣味アプリでは過剰。

**過剰なので入れないもの（明示しておきます）**
- 別立ての SAST サーバ（SonarQube、CodeGuru など）
- DAST（OWASP ZAP など）— 公開環境がない
- コンテナイメージスキャン、IaC スキャン — 対象物がない
- SBOM の生成・署名付きアーティファクト・時限付き例外承認プロセス — 組織向け
- 脆弱性の重大度ごとの SLA、セキュリティチームの承認フロー — チームが1人

### 3. 絶対的な制約の候補（本人がインタビューで明言した場合のみ `discovered-rules.md` に載せる）

以下は**候補**であり、事実でも確定でもありません。本人が「はい、それは絶対」と言った場合にだけ、リードがそのまま1行ルールとして採用してください。言わなければ載せません。2件に絞っています。

- 候補1（`## Forbidden`）: `NEVER シークレット（API キー、トークン、秘密鍵、.env 等の設定ファイル）をリポジトリにコミットしない。キーは環境変数またはリポジトリ外の設定から渡す`
  - 根拠: 2-1 のゲートと `.gitignore` の整備を「なぜやるか」の一文で支える。将来の公開・地図 API 利用のときに効く。
- 候補2（`## Forbidden`）: `NEVER 友達の実データ（実際の写真、実際の位置座標、実名）をテストデータ・サンプル・成果物としてリポジトリに入れない。テストや画面例には架空のデータを使う`
  - 根拠: 扱うのが他人の写真と位置情報であること。趣味アプリでも「預かったものを開発の都合で配らない」線引きがあると、後の共有・位置共有機能の設計が楽になる。

`ALWAYS` 形の候補（ロックファイルを必ずコミットする、など）は「絶対的な制約」というより実践なので、`team-practices.md` の Code Style／Way of Working 側に書くことを勧めます。ルール節には入れません。

### 4. インタビューで本人に聞いてほしいこと（簡潔に、答えられる形で）

いずれもセキュリティパイプラインに関する質問です。5領域のどこに置くかを括弧で示します。

1. **（Deployment / CI）リポジトリの置き場所** — GitHub、GitLab、その他、それともローカルだけ？ 公開リポジトリか非公開か？
   - 理由: シークレット検出と依存関係更新の「組み込み機能が無料で使えるか」がここで決まる。非公開なら Gitleaks のような単体ツールを CI に入れる前提になる。
2. **（Deployment）「CI 緑」の定義にシークレット検出を入れてよいか** — 見つかったらマージ（と `main` への push）をブロックする。選択肢: CI で実行しブロック／CI で実行し警告のみ／入れない。
3. **（Deployment）依存関係の脆弱性監査の厳しさ** — 「修正版がある Critical／High だけブロック、他は警告」でよいか、それとも釣行までは警告のみで、釣行後に厳しくするか。
4. **（Way of Working）`main` への直接コミットを許す場合、直接コミットにも CI を走らせ、赤になったら次の作業より先に直す、でよいか。**
5. **（Code Style / Way of Working）ロックファイルを必ずコミットし、CI はロックファイルどおりにインストールする、でよいか。**（ほぼ「はい」で済む確認）
6. **（絶対的な制約の確認）** 次の2つを「絶対に守る」と言えるか。言えるならそのまま `discovered-rules.md` に載せる。
   - シークレットをリポジトリに入れない（候補1）
   - 友達の実データ（写真・座標・実名）をテストやサンプルに使わない（候補2）
7. **（任意・後回し可）依存関係の自動更新の通知** — 今すぐ／釣行後／要らない。

## Positions

- AGREE: Code Style「選んだスタックの標準リンタ／フォーマッタに従い、マージ前 CI でブロック、ひとりでも外さない」 — 趣味アプリの SAST はリンタで十分で、ここを土台に据えるのが正しい。
- AGREE: Deployment「今回の配布先は本人のスマホ1台、CI 緑＝配布可能、1つ前の緑コミットに戻す」 — 公開環境がないので DAST・コンテナ・IaC のスキャンを持ち込まない判断と整合する。
- AGREE: Way of Working「Construction 前に初回コミットを行う」 — worktree の前提として必要。ただし下の OBJECT の条件付き。
- OBJECT: Way of Working「Bolt 外の小さな修正は `main` に直接コミットしてよい」に、直接コミットへの CI 実行が書かれていない — 直接コミットはシークレット漏えいの最も典型的な経路で、CI がマージ前にしか走らないなら素通りする。「直接コミットにも CI が走り、赤なら先に直す」を条件として併記してほしい。
- OBJECT: Way of Working「初回コミット」の前提条件に `.gitignore` の整備がない — 現状の `.gitignore` には `.env` / `.env.*` も鍵ファイルの拡張子もなく、最初のコミットで入った秘密は squash しても履歴に残る。初回コミット前の整備を前提条件に追加してほしい。
- OBJECT: Deployment「CI 緑」の定義が lint / build / test のみ — シークレット検出と依存関係の脆弱性監査（修正版のある Critical／High のみブロック）を定義に含めてほしい。どちらも導入は数分で、趣味アプリに釣り合う。
- OBJECT: Code Style／Way of Working にロックファイルのコミットと固定インストールの記述がない — サプライチェーンの最低限であり、「1つ前の緑コミットに戻す」が再現できる前提でもある。
- OBJECT: Testing Posture にテストデータの出所（架空データ）の記述がない — 友達の写真・位置情報を扱うアプリなので、実データをフィクスチャに使わないことをテストの作法に含めてほしい（候補ルール2と対応）。
