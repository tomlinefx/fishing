## Intent Analysis（何を達成したいか）

- 目的: 友達と釣りに行くときに使う、自分たちのための釣りアプリを作る。困りごとの解決ではなく、釣りをより楽しむための道具。（intent-statement）
- 最優先の価値: 釣果の記録・共有。次の釣行（1〜2週間以内）当日に、自分の Android スマホで釣果を登録し、一覧を友達にその場で見せられること。（intent-statement、scope-document）[Q5]
- 次の釣行までの最小範囲（期限あり）: 釣果の登録（写真必須）・一覧（新しい順、魚種・場所で絞り込み）・詳細・削除。（scope-document の最小範囲に、本工程で削除と絞り込みを追加）[Q3][Q4][Q9]
- 次の釣行の後（期限なし、価値順）: グループとメンバー（招待）→ 釣果のタイムライン共有 → ポイントの地図 → 釣行中の位置共有。（intent-backlog PU-2〜PU-5）
- 作り方の前提: ひとり開発、トランクベース、test-after、ロジック・保存層は行カバレッジ 80%。（team-practices）

優先度の表記: **Must**＝次の釣行までに必ず／**Should**・**Could**＝次の釣行の後（intent-backlog の優先度に従う）。

## Functional Requirements（機能要件）

### FR1. 釣果の登録（Must）— 画面 S2

- **FR1.1** システムは、写真を1枚添付した釣果を1件保存できなければならない。写真はカメラで撮影するか、端末の写真から選ぶかのどちらかで添付できる。1件に添付できる写真は1枚。[Q1][Q7]（wireframes S2）
  - 受け入れ基準: Given 登録画面を開いている / When カメラで撮影した写真を添付して「保存する」を押す / Then 釣果が1件保存され、一覧の先頭に表示される
  - 受け入れ基準: Given 登録画面を開いている / When 端末の写真から1枚選んで「保存する」を押す / Then 同様に保存される
- **FR1.2** システムは、写真が添付されていない状態では保存を受け付けず、写真の項目の直下に「写真を添付してください」という趣旨の文言を表示しなければならない。[Q1]
  - 受け入れ基準: Given 写真が未添付 / When 「保存する」を押す / Then 保存されず、写真項目の下に文言が出る
- **FR1.3** システムは、任意項目として魚種（文字）・サイズ（cm、数値）・重さ（g、数値）・場所（釣り場の名前、文字）を受け付けなければならない。いずれも空のまま保存できる。[Q1]（scope-document の記録項目、rough-mockups Q4: 場所は文字入力）
  - 受け入れ基準: Given 写真だけ添付 / When 他をすべて空で「保存する」 / Then 保存される
- **FR1.4** システムは、サイズ・重さに数値以外または負の値が入力された場合、保存を受け付けず、その項目の直下に「数字で入力してください」という趣旨の文言を表示しなければならない。（wireframes S2 入力エラー）
  - 受け入れ基準: Given サイズに「abc」 / When 「保存する」 / Then 保存されず、サイズ項目の下に文言が出る
- **FR1.5** システムは、保存した瞬間の日時を釣果に自動で記録しなければならない。利用者はこの日時を入力・変更できない。[Q2]
  - 受け入れ基準: Given 端末の時計が 2026-09-20 06:30 / When 釣果を保存 / Then その釣果の日時が 2026-09-20 06:30 として記録され、詳細に表示される
- **FR1.6** システムは、保存に失敗した場合、画面上部に「保存できませんでした。もう一度お試しください」という趣旨の文言を表示し、入力内容と添付した写真を保持しなければならない。（wireframes S2 保存失敗）
  - 受け入れ基準: Given 保存が失敗する状態 / When 「保存する」 / Then 文言が出て、入力内容が消えない
- **FR1.7** システムは、保存中は「保存する」を再度押せないようにし、二重登録を防がなければならない。（wireframes S2 保存中）
- **FR1.8** システムは、何か入力した状態で「戻る」が押されたとき、「入力を破棄しますか？」の確認を出し、確認後にのみ一覧へ戻らなければならない。（wireframes S2 戻る）

### FR2. 釣果の一覧（Must）— 画面 S1

- **FR2.1** システムは、アプリ起動時に釣果の一覧を最初の画面として表示しなければならない。（rough-mockups Q1）
- **FR2.2** システムは、釣果を日時の新しい順に並べて表示しなければならない。[Q4]（wireframes S1）
  - 受け入れ基準: Given 3件の釣果（9/13 06:00、9/13 07:00、9/12 15:00） / When 一覧を開く / Then 上から 9/13 07:00、9/13 06:00、9/12 15:00 の順
- **FR2.3** システムは、釣果1件を1枚のカードとして、写真・魚種・サイズ／重さ・場所・日付を表示しなければならない。空の任意項目は表示しない。（wireframes S1）
- **FR2.4** システムは、釣果が0件のとき「まだ釣果がありません」という趣旨の文言と「釣果を登録する」ボタンを表示しなければならない。（wireframes S1 空の状態）
  - 受け入れ基準: Given 釣果0件 / When 一覧を開く / Then 空の状態の文言とボタンが出て、ボタンで登録画面が開く
- **FR2.5** システムは、一覧を魚種と場所で絞り込めなければならない。絞り込み中はその条件が画面上で分かり、解除できなければならない。[Q4][Q9]
  - 受け入れ基準: Given アジ2件・メバル1件 / When 魚種「アジ」で絞り込む / Then アジの2件だけが表示され、解除で3件に戻る
  - 受け入れ基準: Given 絞り込み条件に一致する釣果が0件 / When 絞り込む / Then 「該当する釣果がありません」という趣旨の文言が出る（空の状態とは区別する）
- **FR2.6** システムは、一覧から登録画面（＋ボタン）と詳細画面（カードのタップ）へ移動できなければならない。（wireframes S1）
- **FR2.7** システムは、一覧の読み込みに失敗した場合、「釣果を読み込めませんでした」という趣旨の文言と再読み込みの操作を表示しなければならない。（wireframes S1 エラー）
- **FR2.8** システムは、魚種・場所が1行に収まらない場合、一覧では省略して表示し、全文は詳細で表示しなければならない。（wireframes S1 長い文字）

### FR3. 釣果の詳細と削除（Must）— 画面 S3

- **FR3.1** システムは、一覧のカードをタップすると、その釣果の大きな写真・魚種・サイズ／重さ・場所・日時を表示しなければならない。空の任意項目は表示しない。（wireframes S3、rough-mockups Q7）
- **FR3.2** システムは、詳細画面から釣果を削除できなければならない。削除前に「この釣果を削除しますか？」の確認を出し、確認後に削除して一覧へ戻る。[Q3]
  - 受け入れ基準: Given 詳細画面 / When 削除を選び確認する / Then その釣果が一覧から消え、再起動しても戻らない
  - 受け入れ基準: Given 削除の確認 / When キャンセルする / Then 削除されず詳細画面に留まる
- **FR3.3** システムは、釣果の編集（保存後の内容変更）を最小範囲では提供しない。編集は次の釣行の後の要件とする（FR5.6）。[Q3]

### FR4. データの保持（Must）

- **FR4.1** システムは、釣果（写真を含む）を端末の中に保存し、アプリの完全終了・端末の再起動の後も保持しなければならない。[Q6]
  - 受け入れ基準: Given 釣果を1件保存 / When アプリを完全終了して再起動 / Then 一覧にその釣果が表示され、写真も表示される
- **FR4.2** システムは、釣果1件を自己完結した記録（写真・魚種・サイズ・重さ・場所・日時）として保持し、後で他の保存先（クラウド）へ移せる形でなければならない。具体的な形式は設計工程で決める。[Q6]
- **FR4.3** システムは、通信（インターネット接続）がない状態でも FR1〜FR3 のすべてを動作させなければならない。データが端末内にあるため、通信を必要とする処理を最小範囲に含めない。[Q6]（intent-statement: 釣り場で使う）
  - 受け入れ基準: Given 機内モード / When 登録・一覧・詳細・削除を操作 / Then すべて通常どおり動く

### FR5. 次の釣行の後の機能（Should / Could、期限なし）

以下は intent-backlog の PU-2〜PU-5 と、本工程で「後」に回した項目。要件として記録するが、次の釣行までの期限の対象外。詳細な受け入れ基準は、それぞれを作る段階で改めて詰める。

- **FR5.1**（Should, PU-2）システムは、グループを作り、招待リンクまたは招待コードで友達（とその知り合い）が参加できなければならない。（intent-backlog、scope-definition Q5）
- **FR5.2**（Should, PU-3）システムは、グループ全員の釣果を新しい順に並べたタイムラインを表示できなければならない。（intent-backlog、scope-definition Q2）
- **FR5.3**（Should, PU-3 に伴う）システムは、端末内の釣果をクラウドへ移し、グループで共有できなければならない。[Q6]
- **FR5.4**（Could, PU-4）システムは、地図上にピンを立ててメモを書ける釣り場（ポイント）情報を共有できなければならない。（intent-backlog、scope-definition Q6）
- **FR5.5**（Could, PU-5）システムは、釣行中に今いる場所を地図上でグループに共有できなければならない。（intent-backlog、scope-definition Q4）
- **FR5.6**（Should）システムは、保存した釣果の内容（写真・魚種・サイズ・重さ・場所）を編集できなければならない。日時は編集できない。[Q2][Q3]

## Non-Functional Requirements（非機能要件）

- **NFR1 性能**: 一覧画面は、開く操作から1秒以内に釣果のカードが表示されなければならない。釣果が500件あっても、スクロールが引っかからずに動かなければならない（1秒間に60回の画面更新を目安に、目に見える停止がないこと）。[Q8]
  - 判定: 500件のテストデータで、一覧表示までの時間を計測して1秒以内。スクロール中に目に見える停止がない
- **NFR2 対象端末**: Android のスマホで、縦向きの画面で動作しなければならない。開発者本人の端末で動くことが次の釣行までの判定基準。iPhone・PC・タブレットは最小範囲の対象外。[Q5]（rough-mockups Q8、scope-document）
- **NFR3 データ保全**: 保存した釣果は、利用者が削除するまで失われてはならない。アプリの異常終了時も、保存済みの釣果は失われない。[Q6]（FR4.1）
- **NFR4 通信不要**: 最小範囲の機能は通信なしで動作する（FR4.3 と同じ内容を非機能の観点から再掲）。[Q6]
- **NFR5 品質・テスト**: ロジック層と保存層は行カバレッジ 80% 以上。test-after で、ロジック → 保存 → 画面の順に層ごとにテストを書く。整形ツールとリンタの違反があるコードは取り込まない。（team-practices）
- **NFR6 セキュリティ**: 秘密情報（パスワード・API キー）をリポジトリにコミットしない（固定ルール）。釣果のデータと写真は、OS が提供するアプリ専用の保存領域に置き、他のアプリから直接読めない状態にする。最小範囲では外部サービスへの送信を行わない。（team-practices、project.md Forbidden）[Q6]
- **NFR7 アクセシビリティ**: タップ領域は 44px 以上。写真には魚種・サイズ・場所を含む代替テキストを付ける。各画面に見出し（h1）とランドマーク（header／main）がある。（wireframes 各画面のアクセシビリティ注記）
- **NFR8 使いやすさ**: 釣果の登録は1画面で完了し、必須は写真1枚だけ。登録から一覧表示まで、利用者の操作は「＋ → 写真 → 保存」の3操作以内。[Q1][Q7]（rough-mockups Q2）
- **NFR9 保守性**: 画面の文言は1か所にまとめる。画面／ロジック／保存の3層に分け、画面が保存層を直接呼ばない（推奨）。（team-practices）

## Constraints（制約）

- 期限: 次の釣行（1〜2週間以内）までに Must（FR1〜FR4、NFR1〜NFR8）を本人の Android 端末で動かす。（intent-statement）[Q5]
- 体制: ひとりで開発。友達は使う側で、開発中の報告は不要。（intent-statement）
- 範囲: 公開（サーバー・ストアへの配置）と運用は今回の範囲外。（scope-document）
- 技術スタック: 未決定。次の設計工程（Domain Design）で決める。本要件は特定の言語・フレームワークを前提としない。（team-practices）
- 進め方: トランクベース、Bolt ごとの短命ブランチを squash-merge、最初の Bolt は文字だけの一本通し、CI ができるまでは手元の1コマンドが緑であることをマージ条件とする。（team-practices）
- 資料の詳しさ Standard、テストの量 Standard。（aidlc-state.md）

## Assumptions（前提）

- サイズの単位は cm、重さの単位は g とする。[assumption]（Q1 の項目名から。他の単位の要望は出ていない）
- 写真は端末の写真ライブラリを直接参照するのではなく、アプリ専用領域に保存（コピー）する前提で NFR3・NFR6 を書いている。具体的な方式は設計工程で決める。[assumption]
- 最初の一本通し（Bolt 1、文字だけ）の間は FR1.2（写真必須）を一時的に満たさない。PU-1 本体の Bolt で FR1.1〜FR1.2 を満たす。（team-practices の Walking Skeleton）[assumption]
- 絞り込み（FR2.5）の操作方法（一覧上部の選択か、検索欄か）は画面案に描いていない。設計工程で決める。[assumption]
- 通信不要（FR4.3）は「データを端末内に置く」という回答から導いた要件で、本人が直接選んだものではない。固定ルールにはしていない。[assumption]

## Out of Scope（対象外）

- 公開・配布（友達が各自の端末から使える状態にすること）と運用・監視。（scope-document）
- 釣果の編集（最小範囲では対象外。FR5.6 として後に回す）。[Q3]
- 1件に複数枚の写真。[Q7]
- iPhone・PC・タブレット向けの画面。[Q5]
- 最初からクラウドに保存すること。[Q6]
- 釣れたときの条件（天気・潮）の記録（前の工程で選ばれていない。要望があれば後で追加）。

## Open Questions（後の工程で決めること）

- 写真に含まれる位置情報（EXIF の GPS）をそのまま保持するか、取り除くか。友達と共有する段階（FR5.3）までに決める。（practices-discovery の申し送り）
- 絞り込みの操作方法と、削除の取り消し（元に戻す）の要否。設計工程で決める。
- 「1秒以内」「500件」の計測方法（どの端末で、どの状態から測るか）。Build and Test の段階で決める。
