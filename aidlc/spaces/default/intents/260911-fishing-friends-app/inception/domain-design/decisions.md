## ADR-001: 技術スタックに React Native + Expo（TypeScript）を採用する

- **Context** — 対象は Android スマホ1台（NFR2）、ひとり開発、次の釣行まで1〜2週間（requirements 制約）。この計画では非機能・インフラの設計工程を省いているため、Code Generation の前に言語・フレームワークをここで決める必要がある（team-practices: 「domain-design で言語・フレームワークが決まったら」）。カメラ撮影・写真選択・端末内保存・実行時許可という OS 連携が最小範囲に含まれる（FR1.1、FR4.1）。
- **Decision** — React Native + Expo（TypeScript）で作る。Expo の標準モジュール（expo-image-picker、expo-sqlite、expo-file-system、expo-image-manipulator、expo-router）を使い、ネイティブコードは書かない。[Q1]
- **Consequences**
  - 正: 本人が選んだスタックで、TypeScript のツール（整形・リント・テスト）が成熟している。カメラ・保存・許可は Expo のモジュールで完結し、1〜2週間で最小範囲を作り切れる見込み。将来 iPhone にも出せる。
  - 負: ネイティブ（Kotlin）に比べて OS 連携の細部（EXIF、権限の細かな状態）は Expo のモジュールの範囲に縛られる。アプリのサイズと起動時間はネイティブより大きい。Expo のバージョン更新に追従する手間がある。
  - 中立: 端末への載せ方（開発ビルド or EAS Build）は Deployment の手順書で決める（team-practices）。
  - セキュリティ・準拠: 保存先はアプリ専用領域（他アプリから読めない、NFR6）。外部サービスへの送信は最小範囲では行わない。秘密情報は使わない（固定ルール）。依存パッケージはロックファイルで固定し、CI で監査する（team-practices）。
- **Alternatives Rejected**
  - Kotlin + Jetpack Compose: OS 連携が最も素直だが、本人の選択ではない。他 OS へ持っていけない。
  - Flutter: 後で iPhone にも出せるが、本人の選択ではない。
  - PWA: インストール不要だが、カメラ・保存の制約が大きく「自分のスマホに載せる」体験に合わない。

## ADR-002: 部品を CatchLog／CatchStore／CatchUI の3つに分け、依存を一方向にする

- **Context** — team-practices は画面／ロジック／保存の3層と、test-after でロジック → 保存 → 画面の順にテストする方針を定めている。次の釣行の後にクラウド同期（FR5.3）が来ることが分かっている（intent-backlog）。一方で最小範囲は小さく、部品を増やすほど初速が落ちる。
- **Decision** — CatchUI → CatchLog → CatchStore の一方向依存で3部品に分ける。CatchUI は CatchStore を直接呼ばない。Catch エンティティの持ち主は CatchLog。[Q4]
- **Consequences**
  - 正: ロジック層を外部依存なしで単体テストでき、80% の床を守りやすい。クラウド同期は CatchStore の裏側の変更に閉じる。画面案（wireframes）の変更が CatchUI に閉じる。
  - 負: 最小範囲では CatchLog が薄く、部品間の受け渡しコードが増える。
  - 中立: 保存が1種類の間は Repository の抽象インタフェースは切らず、CatchStore を1モジュールに閉じ込めるだけにする（team-practices の推奨どおり）。
  - セキュリティ・準拠: 入力検証を画面→ロジックの境界で1回だけ行う場所が定まる（team-practices）。
- **Alternatives Rejected**
  - 2部品（CatchCore／CatchUI）: 保存方式の変更がルール側に波及し、ロジックの単体テストが保存に引きずられる。
  - 1部品（フォルダ内でファイル分けのみ）: 境界がコード上で強制されず、画面→保存の直呼びが混入しやすい。

## ADR-003: 釣果は端末内の SQLite に、写真はアプリ専用領域に原本＋縮小版で保存する

- **Context** — 端末内保存で、後でクラウドへ移せる形（FR4.2）、再起動後も残る（FR4.1）、500件で一覧1秒以内（NFR1）、写真1枚必須（FR1.1）、他アプリから読めない（NFR6）が要件。写真の原本は数 MB あり、一覧で500件分をそのまま読むと重い。
- **Decision** — 釣果（写真以外）は SQLite（expo-sqlite）に1件＝1行で保存し、並び順と絞り込みは SQL で行う。写真は撮影／選択時にアプリ専用領域へコピーし、一覧用の縮小版を生成して、原本と縮小版のパスを行に持たせる。削除時は行と両ファイルを消す。[Q2][Q3]
- **Consequences**
  - 正: 絞り込み・並び順がデータベース任せで速い。1件1行の自己完結した形なので、クラウドへ移すときに行をそのまま書き出せる。原本が端末の写真ライブラリから消えても釣果は残る。一覧は縮小版だけを読むので軽い。
  - 負: 写真を二重に持つため容量を使う。縮小版生成の分だけ保存が遅くなる（体感に影響しない範囲に収める）。スキーマの版上げの仕組みが必要になる。
  - 中立: 縮小版の寸法・画質は Functional Design で決める。
  - セキュリティ・準拠: アプリ専用領域は OS が他アプリから隔離する。EXIF の GPS はコピー時に保持し、共有段階で扱いを決める（requirements Open Questions）。
- **Alternatives Rejected**
  - JSON ファイル1つ: 単純だが、件数が増えると全件読み込みで遅くなり、絞り込みも自前実装になる。
  - Key-Value ストア: 設定向けの仕組みで、一覧の並び順・絞り込みに向かない。
  - 写真の参照のみ保持: 容量は節約できるが、元写真を消すと表示できず FR4.1 を満たせない。縮小版なし: 500件の一覧で原本を読むことになり NFR1 が危うい。

## ADR-004: 釣果の ID は端末側で生成する UUID にする

- **Context** — 後で友達の釣果とクラウドで混ざる（FR5.2、FR5.3）。端末内の連番は端末ごとに重複する。
- **Decision** — 保存時に CatchLog が UUID（v4 相当）を生成し、Catch の識別子にする。[Q5]
- **Consequences**
  - 正: 複数端末の釣果を統合しても衝突しない。クラウド側で ID を振り直す必要がない。
  - 負: 連番より読みにくく、デバッグ時に目視で追いにくい。
  - 中立: 並び順は id ではなく caughtAt で決める（FR2.2）。
  - セキュリティ・準拠: 推測しにくい ID なので、将来 URL などに出しても列挙されにくい。
- **Alternatives Rejected**
  - 端末内の連番: クラウド統合時に振り直しが必要で、FR4.2 の「そのまま移せる形」に反する。

## ADR-005: カメラ・写真の許可拒否時は案内と設定導線を出し、写真なし保存は許さない。対応 Android は本人の端末のバージョン以上

- **Context** — 要件チェックの指摘 R-01（許可拒否時の挙動が未定義）と R-03（対象 Android バージョンが未定義）。写真は必須（FR1.2）。Android は実行時に許可を求め、拒否されると再要求できない場合がある。
- **Decision** — 許可が拒否されたら「写真を添付するには許可が必要です」と表示し、端末の設定画面を開く導線を出す。FR1.2 の例外は作らない。対応 Android は本人の端末のバージョンを下限とし、Code Generation の前に端末で確認して `minSdkVersion` 相当の設定に反映する。[Q6][Q7]
- **Consequences**
  - 正: 「写真必須」というルールが例外なく保たれ、要件と実装が一致する。対象バージョンを1つに絞ることで動作確認が本人の端末1台で済む。
  - 負: 許可を出すまで釣果を登録できない。友達の端末が古い場合は後で下限を下げる判断が要る（FR5 の段階）。
  - 中立: 設定画面を開く導線は Expo の Linking で実装する。
  - セキュリティ・準拠: 許可の要求は必要になった時点（写真ボタンのタップ時）で行い、起動時にまとめて要求しない。
- **Alternatives Rejected**
  - 拒否時に限り写真なし保存を許す: 要件の例外が増え、一覧・詳細の「写真なし」表示を最小範囲に持ち込む。
  - 現行から2世代前まで／最新版のみ: 前者は確認の手間、後者は本人の端末が最新でない可能性があり、いずれも本人の選択ではない。

## ADR-006: 一覧の絞り込みは上部の選択チップ（魚種・場所）で行う

- **Context** — 絞り込みは最小範囲（FR2.5）だが、画面案には操作方法が描かれていない。釣り場では片手・短時間の操作が多い。
- **Decision** — S1 の上部に「魚種」「場所」の選択チップを置き、タップで登録済みの値の一覧から選ぶ。選択中はチップが強調され、もう一度タップで解除する。候補は CatchLog が算出する。[Q8]
- **Consequences**
  - 正: 文字入力が不要で、屋外・片手でも使える。表記揺れ（「アジ」と「あじ」）は候補として並ぶだけで、絞り込みの取りこぼしにならない。
  - 負: 登録済みの値が増えると候補が長くなる（最小範囲では許容。件数が増えたら検索欄を足す）。
  - 中立: 画面案（wireframes S1）にチップ行を追加する変更は Functional Design の画面設計で反映する。
  - セキュリティ・準拠: 影響なし。
- **Alternatives Rejected**
  - 検索欄（部分一致）: 釣り場での文字入力は手間で、表記揺れで取りこぼす。
  - チップと検索欄の両方: 最小範囲としては過剰。
