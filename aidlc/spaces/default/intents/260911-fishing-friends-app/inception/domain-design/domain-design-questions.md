## Q1. Android アプリを何で作りますか？（技術スタック）

1〜2週間でひとりで作るので、「自分が使い慣れているか」が最大の判断材料です。慣れた言語があれば X. Other で教えてください。

- A. Kotlin + Jetpack Compose（Android 標準。カメラ・保存・権限の扱いが最も素直。他 OS には持っていけない）
- B. Flutter（Dart。画面が作りやすく、後で iPhone にも出せる。カメラ・保存は公式プラグイン経由）
- C. React Native + Expo（TypeScript。JavaScript に慣れていれば速い。カメラ・保存は Expo のモジュール経由）
- D. スマホのブラウザで動く Web アプリ（PWA。インストール不要だが、カメラ・保存の制約が大きく、「アプリとして入れる」体験にならない）
- E. まだ決めていない（おすすめを提案してほしい）
- X. Other (please specify)

[Answer]: C

## Q2. 釣果のデータ（写真以外）はどう保存しますか？

「後でクラウドへ移せる形」（FR4.2）と「500件でも一覧が1秒以内」（NFR1）の両方を満たす方式を決めます。

- A. 端末内の SQLite 系データベース（Room / Drift / SQLite 相当）に釣果1件＝1行で保存する。絞り込みと並び順はデータベースに任せる（推奨）
- B. JSON ファイル1つに全件を保存し、起動時に読み込む（単純だが件数が増えると遅くなる）
- C. Key-Value ストア（設定保存用の仕組み）に保存する
- D. まだ決めていない
- X. Other (please specify)

[Answer]: A

## Q3. 写真はどう保存しますか？

- A. 撮影／選択した写真をアプリ専用の保存領域にコピーし、一覧用の縮小版も作る（元の写真が消えても残る。一覧が軽い）（推奨）
- B. アプリ専用領域にコピーするが、縮小版は作らない（実装が少し楽。500件の一覧で重くなる可能性）
- C. コピーせず、端末の写真ライブラリ上の元写真への参照だけを保持する（容量を使わないが、元写真を消すと表示できなくなる）
- D. まだ決めていない
- X. Other (please specify)

[Answer]: A

## Q4. 部品（構成要素）の分け方はどれにしますか？

チームルールの3層（画面／ロジック／保存）を、コードの部品としてどう切るかです。

- A. 3つに分ける: CatchLog（釣果のルールとデータの形：必須チェック・数値検証・並び順・絞り込み）／CatchStore（端末内への保存と読み出し、写真ファイルの管理）／CatchUI（一覧・登録・詳細の画面）。画面は CatchLog だけを呼び、CatchLog が CatchStore を呼ぶ（推奨: 後でクラウド同期を足すとき CatchStore の差し替えで済む）
- B. 2つに分ける: CatchCore（ルール＋保存を一体）／CatchUI（画面）。小さく速いが、保存方式を変えるときにルール側も触る
- C. 1つの部品にまとめる（機能フォルダ `catches/` の中で層をファイルで分けるだけ）。最速だが、境界がコード上で強制されない
- D. まだ決めていない
- X. Other (please specify)

[Answer]: A

## Q5. 釣果1件を識別する ID はどう決めますか？

後で友達の釣果とクラウドで混ざったときに、同じ ID がぶつからない形にしておく必要があります（FR4.2）。

- A. 端末側で生成する UUID（世界で重複しない乱数の ID）。クラウドに移しても衝突しない（推奨）
- B. 端末内の連番（1, 2, 3…）。クラウドに移すときに振り直しが必要
- C. まだ決めていない
- X. Other (please specify)

[Answer]: A

- C. まだ決めていない
